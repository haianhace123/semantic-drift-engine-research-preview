# Semantic Drift Engine API Reference

## 1. Scope

This document describes the supported public integration surface of Semantic Drift Engine.

It intentionally does not document internal worker authorization, claim, fencing, or physical execution functions as public APIs.

The canonical interactive OpenAPI schema is generated by FastAPI at runtime.

## 2. Authentication Models

SDE has two primary authentication contexts.

### User session authentication

Dashboard, temporal workspace, alert-management, account, and API-key-management operations use the authenticated user/session boundary.

### API-key authentication

Public lineage integration uses organization-scoped API keys with explicit permissions.

The organization associated with the authenticated API key defines the tenant context. Callers should not be trusted to select another organization through request payloads.

## 3. System Endpoints

### `GET /health`

Liveness probe.

This confirms that the API process is alive.

It intentionally does not require PostgreSQL or Redis to be healthy.

### `GET /ready`

Readiness probe.

Use this when deciding whether the API should receive dependency-backed production traffic.

## 4. Public Lineage API

The supported lineage surface is:

```text
POST /api/lineage/execution-target-bindings
POST /api/lineage/observations
POST /api/lineage/impact
POST /api/lineage/temporal-invalidation-analysis
POST /api/lineage/invalidation-decisions/query
GET  /api/lineage/invalidation-decisions/{decision_id}
GET  /api/lineage/temporal-invalidation-resolution/{event_id}
POST /api/lineage/invalidation-execution-verifications
```

Execution authorization is intentionally not exposed as an API-key integration endpoint.

## 5. Publish Execution Target Binding

### `POST /api/lineage/execution-target-bindings`

Publishes an immutable logical execution-target binding for the organization associated with the authenticated API key.

The request requires API-key `write` permission.

The client does not supply an organization identifier. Tenant ownership is derived from the authenticated API key.

Bindings are immutable revisions:

- an exact replay of the same revision is idempotent,
- conflicting content for an existing revision fails closed,
- revision gaps fail closed,
- updates are represented by publishing the next revision rather than mutating an existing revision.

Binding configuration contains logical deployment references rather than physical credentials.

For database-backed execution, a binding can refer to a logical `connection_ref`. Deployment maps that reference to the physical connection URL through `SDE_DOWNSTREAM_DATABASE_URLS`.

## 6. Submit Lineage Observation

### `POST /api/lineage/observations`

Records exact lineage evidence.

Observation kinds supported by the request model include:

```text
materialization
consumption
```

A dependency reference includes:

```json
{
  "asset_external_id": "source-document",
  "revision_external_id": "revision-17",
  "dependency_type": "derived_from"
}
```

`dependency_type` defaults to:

```text
derived_from
```

when omitted.

Use stable external asset and revision identifiers from the source or retrieval system. Do not replace exact revision identity with semantic similarity or a reconstructed guess.

### Instrumentation requirement

If exact lineage is required, submit the observation while the consuming system still knows the exact upstream revision.

Once provenance has been discarded, SDE cannot truthfully recreate exact consumption lineage from embeddings or entity relationships alone.

## 7. Analyze Impact

### `POST /api/lineage/impact`

Requires an API key with:

```text
read
```

permission.

The request identifies an exact lineage revision.

The response represents downstream impact reachable through recorded dependency evidence and can include causal paths.

The following states are semantically different:

```text
lineage unavailable
```

```text
lineage available with zero downstream impact
```

Clients must not collapse these states.

## 8. Analyze Temporal Invalidation

### `POST /api/lineage/temporal-invalidation-analysis`

Requires an API key with:

```text
write
```

permission because successful analysis can persist immutable invalidation decisions.

The request identifies a temporal drift event:

```json
{
  "event_id": "<event-uuid>"
}
```

The client does not supply an organization identifier. The event is resolved within the tenant associated with the authenticated API key.

Analysis requires completed semantic and vector change evidence. Events whose required evidence is not ready fail closed.

For a ready event, SDE resolves exact lineage roots correlated with the old snapshot and analyzes each root using the canonical invalidation policy. The response contains the event identity, old and new snapshot identities, and the persisted decisions grouped by root analysis.

A ready event with no correlated lineage roots succeeds with an empty `analyses` collection. This represents a deterministic no-op and is distinct from an event whose evidence is not ready.

Repeating the same request is replay-safe: existing immutable decisions are returned rather than duplicated.

This endpoint does not activate policy authority, authorize execution, or execute downstream invalidation.

## 9. Query Invalidation Decisions

### `POST /api/lineage/invalidation-decisions/query`

Requires an API key with:

```text
read
```

permission.

The request identifies the lineage revision whose associated invalidation decisions should be discovered.

This endpoint is intended for decision discovery, not execution.

## 10. Get Invalidation Control-Plane Record

### `GET /api/lineage/invalidation-decisions/{decision_id}`

Returns the control-plane projection for a specific invalidation decision.

The representation separates concepts such as:

- the decision,
- policy information,
- current eligibility,
- execution intent,
- execution attempts,
- execution results,
- post-repair verification.

Consumers should preserve these distinctions.

Historical execution does not imply current eligibility, and current eligibility does not imply that execution has already occurred.

`execution.verification` is `null` unless the latest terminal execution result succeeded. For a successful result, verification has one of these states:

- `awaiting_evidence`: no currently qualifying post-repair materialization evidence is bound to the successful execution result (an older or superseded binding may still be returned for audit),
- `stale_dependency_present`: bound materialization evidence still contains the exact stale direct predecessor identified by the persisted decision,
- `verified`: bound materialization evidence no longer contains that exact stale direct predecessor.

These states are deliberately narrower than a global safety verdict. `verified` does not mean that the entire downstream system is globally safe, repaired, resolved, or that integrity has been restored in every sense.

## 11. Get Temporal Invalidation Resolution

### `GET /api/lineage/temporal-invalidation-resolution/{event_id}`

Requires an API key with `read` permission.

This endpoint reconstructs the persisted control-plane resolution for a temporal drift event from durable event-to-decision provenance. It does not rerun the dependency graph or reevaluate historical policy decisions.

The response identifies the event, its old and new snapshots, and the associated invalidation control-plane records. Each decision retains its persisted historical decision while current eligibility is evaluated separately and execution reflects persisted lifecycle state.

Successful executions also expose the post-repair verification state described above.

Unknown events and events belonging to another tenant return `404` with `LINEAGE_008`.

## 12. Publish Post-Repair Verification Evidence

### `POST /api/lineage/invalidation-execution-verifications`

Requires an API key with `write` permission.

The request explicitly binds a successful terminal execution result to the materialization observation that provides causal post-repair evidence:

```json
{
  "execution_result_id": "<execution-result-uuid>",
  "observation_id": "<materialization-observation-uuid>"
}
```

The response contains:

```json
{
  "id": "<verification-record-uuid>",
  "execution_result_id": "<execution-result-uuid>",
  "observation_id": "<materialization-observation-uuid>",
  "created_at": "<timestamp>",
  "created": true
}
```

An exact replay is idempotent and returns the existing binding with `created: false`.

The referenced execution result must be successful. The observation must be a `materialization` observation for the exact persisted decision target. A result already bound to a different observation cannot be rebound through this endpoint.

Error semantics are:

- `LINEAGE_010` / `404`: the execution result or observation is not visible in the authenticated tenant,
- `LINEAGE_011` / `409`: the resources exist but do not constitute valid verification evidence,
- `LINEAGE_012` / `409`: the execution result is already bound to a different observation.

Publication records explicit causal evidence only. The client does not submit a verification state. The read projection determines whether the bound evidence is `stale_dependency_present` or `verified`.

For a new binding, the observation must be a different target revision ingested strictly after the successful result was recorded, and must be the latest target materialization at publication. A previously bound observation that no longer qualifies, or was superseded, projects as `awaiting_evidence`; its binding remains available for audit. The target integrity query does not treat such evidence as `verified`.

`created_at`, observation sequence, and target revision advancement are necessary rejection fences, not causal proof of physical repair. The trusted source still must attest actual post-repair collection.

This endpoint does not activate policy authority, authorize execution, execute downstream work, or install deployment credentials.

## 13. Error and Tenant Semantics

Lineage resources are tenant-scoped.

A caller must not be able to use resource identifiers to cross an organization boundary.

Clients should treat resource-not-found responses as authoritative rather than attempting to infer whether an identifier exists in another tenant.

The public error envelope should be consumed according to the runtime OpenAPI/API behavior. Error-envelope normalization remains an area that should be stabilized before publishing a generated SDK.

The active product workflow consumes temporal data such as:

## 13. Alert APIs

Alert-management routes are mounted under:

```text
/api/alerts
```

and are protected by authenticated user context in the main application.

Alert delivery is handled asynchronously by the alert delivery worker deployed in the current Compose topology.

### Webhook delivery contract

Webhook delivery is at-least-once. A destination can accept a request before the worker durably records delivery success, so receivers must handle duplicate requests idempotently.

Each webhook request includes:

```text
X-SDE-Delivery-ID
X-SDE-Delivery-Key
X-SDE-Timestamp
X-SDE-Signature
```

`X-SDE-Delivery-ID` identifies the durable delivery record.

`X-SDE-Delivery-Key` is the stable logical delivery identity for an alert and destination. Receivers should use this value as the idempotency key when deduplicating retries.

`X-SDE-Timestamp` is the Unix timestamp used when the request signature is generated.

`X-SDE-Signature` contains an HMAC-SHA256 signature in this form:

```text
sha256=<hex digest>
```

The signed bytes are constructed exactly as:

```text
timestamp + "." + delivery_id + "." + delivery_key + "." + raw_request_body
```

The timestamp, delivery ID, and delivery key are the UTF-8 byte representations of the corresponding header values. The separators are literal ASCII `.` bytes. The request body is appended as the raw bytes received over HTTP.

Receivers should verify the signature against the raw request body before parsing or reserializing JSON. Signature comparison should use a constant-time comparison function. Receivers should also reject timestamps outside their accepted replay window.

A delivery key should be recorded as successfully processed only after the receiver's business operation succeeds. If the same delivery key is received again, the receiver should return a successful response without repeating a completed non-idempotent side effect.

Semantic Drift Engine does not claim exactly-once webhook delivery.

## 15. API-Key Integration Guidance

For production lineage instrumentation:

1. Create an API key for the intended organization.
2. Grant only the permissions required by the integration.
3. Store the raw key in a secret manager.
4. Publish logical execution-target bindings when downstream invalidation is required.
5. Preserve stable upstream asset and revision identifiers.
6. Submit lineage observations before provenance is lost.
7. Use temporal invalidation analysis when reacting to a completed temporal drift event.
8. Use direct impact analysis when starting from an exact lineage revision rather than a temporal event.
9. Query persisted invalidation decisions independently when decision discovery is required.
10. Retrieve the control-plane record when execution history or current eligibility is needed.

Do not embed organization authority in client-controlled identifiers.

API-key `write` permission does not itself grant execution authority. Execution authorization is an explicit operator action outside the public integration API.

## 16. Internal Execution Boundary

Policy activation and execution authorization are supported operator authority operations.

Activate a policy revision with:

```text
python -m scripts.lineage_authority activate-policy --organization-id <organization-uuid> --policy-external-id <policy-id> --revision <revision>
```

Authorize an eligible persisted decision with:

```text
python -m scripts.lineage_authority authorize-execution --organization-id <organization-uuid> --decision-id <decision-uuid>
```

These operations are intentionally separate from API-key-authenticated application integration.

After authorization, the lineage invalidation executor can process authorized work:

```text
python -m scripts.run_lineage_invalidation_executor
```

The executor does not auto-authorize decisions.

Claiming, fencing, target resolution, physical invalidation, and immutable result persistence remain internal execution mechanics rather than public application endpoints.

## 17. OpenAPI

FastAPI remains the canonical source for exact generated schemas, validation constraints, and response models.

When documentation and generated OpenAPI disagree on field-level details, treat the running version's OpenAPI schema as the executable contract and correct this document before release.
